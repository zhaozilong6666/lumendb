# 复制路径基准（第 4 层）

> 实测日期：2026-11-14。
> 跑法：`python -m bench.replication --rows 2000 --repeat 3 --out bench/results/replication.md`
> 原始表格见 `bench/results/replication.md`。数字会随机器、磁盘负载变化。

## 场景

- 主库 `checkpoint_wal_bytes=0`，避免自动 checkpoint 干扰观察。
- 先建 2000 行表，基准备份在 200 行时创建；其余 1800 行在副本启动后写入。
- 副本通过 `WALServer` 的 TCP `backup_stream` 拉基准备份，再以
  `max_records=1000` 分批 `replicate`，每批 apply 后 `ack`。
- `lag_from_server` 读取主库 `status` 的 `last_lsn` 与副本 `applied_lsn` 之差；
  单位是 WAL 逻辑字节，不是表数据字节。

## 优化前（Windows 本地，单区间页 diff）

| 指标 | 数值 |
|---|---:|
| 数据行数 | 2000 |
| 基准备份（最好 / 中位） | 0.020 s / 0.034 s |
| 主库写入 1800 行（中位） | 0.400 s |
| 副本追平（最好 / 中位） | 1.275 s / 3.215 s |
| 应用记录数 | 7376 |
| 应用吞吐 | 约 5,783 记录/秒（最好样本） |
| 写入后 LSN 延迟 | 13,896,882 字节 |
| 追平后 LSN 延迟 | 0 字节 |
| 副本 `COUNT(*)` | 16.91 ms |
| 主库数据文件 | 212,992 B |

解读：2000 行数据文件只有 213 KB，但一轮 WAL 到 15.5 MB（约 7.7 KB/行）。
主要来源不是 `PAGE_IMAGE`（新页镜像约 100 KB），而是 B+ 树叶页的页内 diff：
每次插入会改页头计数、页首记录区和页尾槽位目录，单区间 before/after 切片
经常把中间整片零区一起写进 WAL。副本按 `pageLSN` 幂等重放，正确性不依赖
WAL 大小，但吞吐和传输成本被放大。

## 优化后（Linux 云主机，多区间页 diff）

`_commit_page` 现在用 `_diff_ranges` 把互不相连的变化拆成多条 UPDATE 记录；
间隔小于 8 字节的区间合并，变化超过 32 条时退回单区间，避免日志记录数爆炸。
多条记录仍按 `pageLSN` 顺序重放，恢复/复制语义不变。

| 指标 | 数值 |
|---|---:|
| 数据行数 | 2000 |
| 基准备份（最好 / 中位） | 0.003 s / 0.004 s |
| 主库写入 1800 行（中位） | 0.851 s |
| 副本追平（最好 / 中位） | 0.396 s / 0.398 s |
| 应用记录数 | 10996 |
| 应用吞吐 | 约 27,792 记录/秒 |
| 写入后 LSN 延迟 | 1,111,380 字节 |
| 追平后 LSN 延迟 | 0 字节 |
| 副本 `COUNT(*)` | 10.72 ms |
| 主库数据文件 | 212,992 B |

同一 2000 行场景，写入后 WAL 延迟从 13.9 MB 降到 1.11 MB（约 12.5×），
应用吞吐从 5.8k 记录/秒升到 27.8k 记录/秒（约 4.8×）。记录数变多是因为
一条页修改被拆成多条小记录，但总字节数显著下降。不同机器/磁盘的绝对值
不可直接比较，优化前后在同一天的两次运行也只作为相对参考。

## 丢失窗口与提升

- 主库在写入后立即崩溃、副本尚未 apply 时，最多丢失约 1.1 MB WAL 对应的
  已提交事务（优化后场景）；这是物理复制的 RPO 窗口，不是 RPO=0。
- `Replica.promote` 只保留已复制前缀；`test_promote_keeps_only_replicated_prefix`
  固定了这一语义。
- `promote(fence_path=...)` 会写 `PromotionFence` marker；配置了同一 marker
  的旧主库会在下一笔写上拒绝。共享 marker 不存在时，旧主仍可能继续写，
  因此部署必须把 fence 文件放在两个节点都能看到的位置。
- `ReplicationMonitor` 连续网络失败达到阈值后自动调用同一个 `promote`；
  逻辑错误（槽位已回收）返回 `needs_attention`，不会自动提升。

## 下一步（按优先级）

- 进一步把叶页 diff 变成记录级/槽位级日志，减少“页头计数 + 多条小记录”
  的记录数开销；当前先保留物理语义，不牺牲恢复正确性。
- 增量/压缩基准备份；完整基准备份已改为 `snapshot_file` + `backup_stream`
  分块传输，不再整库读进内存，但仍是全量拷贝。
- 复制流 TLS、压缩、二进制帧、长连接/心跳；当前是换行 JSON + base64，
  已支持共享 token 认证但不是加密传输。
- 自动提升只有连续失败阈值，没有心跳租约/仲裁和客户端重定向。
- 副本查询与 apply 的并发调度：当前 `Replica._lock` 串行化 apply 与查询，
  先保证不读到半批状态。
