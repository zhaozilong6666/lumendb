# 副本读一致性：`snapshot_read` 与一个尚未修的缺口（2026-11-17）

## 能做什么

`Replica.snapshot_read()` 把一段**多条语句**的只读工作固定在同一个已应用前缀上：

```python
with replica.snapshot_read():
    a = replica.execute_one("SELECT COUNT(*) FROM a")
    b = replica.execute_one("SELECT COUNT(*) FROM b")
```

上下文期间持有数据锁，`apply` 会把剩余记录**一次性应用完**，所以两次查询看到的是
同一个前缀。代价是这段时间副本的 apply 停摆——只用于确实需要跨语句一致性的短读。

`snapshot_read` 是不可重入计数（同一线程可以嵌套，退出要一一对应），异常退出也会
把计数还回去，测试见 `tests/unit/test_replica_snapshot_read.py`。

## 尚未修的缺口（重要）

**默认的单语句读在组边界上仍可能看到"半个事务"的中间态。**

`Replica.apply` 为不让长批饿死读者，按 `_apply_chunk_size`（默认 512）分组、组间
释放数据锁。而一条 SQL 的 DML 会拆成**多条 WAL 记录**（表页一条、每个索引页各一条），
于是组边界可能落在"表页已应用、索引页还没应用"的位置：

- 顺序扫描能看到新行、索引扫描看不到 → 同一个读者前后两次查询对不上；
- 极端时读者会读到页头计数与槽位数组打架的半个页（`BTreeInvariantError`）。

### 复现

把分片调小（`replica._apply_chunk_size = 1`）放大窗口，400 行插入 + 一个二级索引，
一个线程持续 apply、一个线程反复 `SELECT COUNT(*) FROM t` 与
`SELECT COUNT(*) FROM t WHERE v >= 0` 对比：

```
顺序扫描 vs 索引扫描不一致次数: 197
前几个不一致样本: [(51, 50), (51, 50), ...]
BTreeInvariantError: 叶子页 6 的槽位 50 偏移越界：0
```

探针：`D:\projects\lumendb-review\_probe_snapshot.py`（`PYTHONPATH` 指向仓库后运行）。
默认 512 的分组只是把窗口变小，不消除它。

### 尝试过但不成立的做法

| 做法 | 结果 |
|---|---|
| 组边界对齐到事务结束记录（向后找最近的 COMMIT） | 无效。组起点由上一组决定，仍可能落在一个事务中间；实测不一致次数没有下降（197 → 197），还因为组变大而让 apply 更慢 |
| 组边界对齐到事务开始（向前找 COMMIT） | 更差：直接退化成每 1 条记录一组，不一致反而增多（129 → 197） |
| 让读者只走 MVCC 可见性检查 | 不够。MVCC 能把**未提交的行**挡住，但挡不住**索引结构**层面的中间态：索引页记录的更新可能晚于表页记录，索引扫描会漏掉已提交的行 |

### 正确的方向（未做，属第 4 层剩余差距）

1. **原子应用单元 = 事务**：apply 一次拿锁应用完**整个事务的所有记录**（从 BEGIN 到
   COMMIT），中间不释放锁。代价是长事务期间读者被饿死——需要配一个"最大等待"降级
   策略（超时就让读方重试）。
2. **复制流按事务边界取批**：`fetch` 返回的批必须从"事务开始"到"事务结束"，否则
   首组/尾组必然切在事务中间。这要求 `WALClient.fetch` 接受"对齐到最近 COMMIT"的
   语义，并在 follower 侧维护"未完成事务"的缓冲。
3. **索引项 MVCC**：与写并发的三条阻塞同源（见 `docs/concurrency.md` 第 2 步），
   属于重做存储引擎的范围。

**当前缓解**：需要跨语句一致性的读者用 `snapshot_read()`；单语句读的风险集中在新页
分配/索引分裂瞬间，正常负载下窗口很小，但**不能宣称"副本读永远一致"**。

## 与写并发的阻塞同源

`docs/concurrency.md` 第 2 步列出的三条真实阻塞之一是"唯一索引项在 DELETE 时被物理
删除，并发 INSERT 看不到"。副本这个缺口是同一件事的读侧表现：**索引结构与表数据的
更新不是一个原子单元**。两条路要一起修，靠索引项 MVCC 或事务级 apply 单元。
